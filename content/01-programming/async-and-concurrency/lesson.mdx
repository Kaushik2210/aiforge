# Async and Concurrency

> **Realm 1, Programming Fundamentals.** Guide: *Mira*, the lantern-bearer
> (an original AIForge character). One lamplighter walks a road with many
> lanterns: while one wick catches, she tends the next. She is not faster; she
> just never stands idle.

Most AI engineering code spends its life waiting: for a model API to answer,
for a download, for a database. If you wait for each call before starting the
next, a task that could take two seconds takes twenty. Async code lets one
program keep many such waits going at once. It also underlies most modern
Python web frameworks and LLM client libraries, so you will meet it constantly.

---

## L1. Intuition

**A cook with several pots.** A cook who watches one pot until it boils, then
starts the next, is slow. A cook who puts all the pots on, then checks each as
it boils, finishes sooner, even though there is still only one cook. Waiting
is the part that overlaps.

```python
import asyncio

async def boil(name, seconds):
    await asyncio.sleep(seconds)      # "wait for the pot": others can run now
    return name

async def main():
    results = await asyncio.gather(boil("rice", 0.2), boil("eggs", 0.1))
    print(results)                    # ['rice', 'eggs']

asyncio.run(main())
```

**`await` marks the places a task may pause.** Waiting for something that is not
ready yet hands control back; awaiting something that finishes at once does
not. Between those points a coroutine runs without interruption. The *event
loop* is the manager that decides which paused task to resume next.

**It is cooperative.** Nothing forces a task to pause. A task must choose to
`await`. That makes async code easy to reason about, and it is why one
badly behaved task can stall everything.

<Callout type="warn" title="Where the cook picture breaks">
A person can be called away by a shout or a timer. An event loop is never
interrupted: it only gets control back when a coroutine awaits something that is
not ready, or finishes. A coroutine that computes for ten seconds without
awaiting holds every other task for ten seconds.
</Callout>

## L2. Mechanics

### Coroutines and `await`

```python
async def double(n):
    return n * 2

double(5)            # a coroutine object; nothing has run yet
await double(5)      # 10, inside another async def
asyncio.run(double(5))   # 10, from ordinary code
```

Forgetting the `await` gives you the coroutine object instead of the result,
and Python prints a `RuntimeWarning: coroutine ... was never awaited`.

### One after another versus together

```python
async def work(n, d=0.1):
    await asyncio.sleep(d)
    return n * 2

async def sequential():
    return [await work(1), await work(2), await work(3)]   # about 0.3 s

async def together():
    return await asyncio.gather(work(1), work(2), work(3)) # about 0.1 s
```

Both return `[2, 4, 6]`. `gather` returns results in the order you passed the
awaitables, even if a later one finishes first.

### Tasks

`asyncio.create_task(coro)` schedules a coroutine to run on the loop and gives
you a `Task` to await later. The task does not start running until the current
coroutine reaches an `await` that actually pauses (here, awaiting the task):

```python
async def main():
    t = asyncio.create_task(work(1))
    print("created")          # printed first
    print(await t)            # the task runs while we wait
```

### Blocking code blocks everyone

```python
async def ticker():          # prints a tick every 0.1 s
    ...
async def bad():
    time.sleep(0.3)          # blocks the whole thread: no tick can happen
```

While `bad` sleeps, the ticker is frozen. With `await asyncio.sleep(0.3)` the
ticker keeps ticking. For blocking functions you cannot replace, run them in a
thread:

```python
result = await asyncio.to_thread(slow_blocking_function, arg)   # Python 3.9 and later
```

Because of the global interpreter lock, a worker thread helps mainly when the
function spends its time waiting (I/O), not computing.

### Errors and timeouts

```python
try:
    async with asyncio.timeout(0.05):
        await asyncio.sleep(1)
except TimeoutError:
    ...
```

`asyncio.timeout` cancels the work and raises `TimeoutError` when the time is
up. A `TaskGroup` runs several tasks together and, if one fails, cancels the
others and raises an `ExceptionGroup`. Both were added in Python 3.11; on older
versions use `asyncio.wait_for` and `gather`:

```python
async with asyncio.TaskGroup() as group:
    group.create_task(work(1))
    group.create_task(work(2))
# leaving the block waits for both
```

### Limiting how many run at once

Starting 1,000 requests at once may overload a server. A semaphore lets only a
few in at a time:

```python
sem = asyncio.Semaphore(2)

async def limited_job():
    async with sem:          # at most 2 tasks are inside this block
        await asyncio.sleep(0.05)
```

### Threads and processes

| Tool | Good for | Why |
|---|---|---|
| `asyncio` | many waits on the network or disk | one thread, switches at `await` |
| threads (`concurrent.futures.ThreadPoolExecutor`) | blocking libraries that wait | waiting overlaps; the global interpreter lock lets only one thread run Python code at a time |
| processes (`ProcessPoolExecutor`, `multiprocessing`) | heavy computation | each process has its own interpreter and lock |

<Step prompt="what does asyncio.gather(work('slow', 0.2), work('fast', 0.05)) return, and in what order?">
The list holds the slow result first and the fast one second. `gather` keeps
the order of its arguments, so the slow one comes first even though it
finished last.
</Step>

## L3. Build it

AIForge runs your Python in the browser with Pyodide, which has its own event
loop and its own limits: its documentation says threads and multiprocessing are importable but not
functional there, and its default loop cannot block the way a normal event loop
does (newer Pyodide versions can, where the JavaScript runtime supports stack
switching). When
AIForge's test setup tried `asyncio.run` in Pyodide under Node it raised
`RuntimeError: WebAssembly stack switching not supported in this JavaScript
runtime`, so the in-browser runner cannot be relied on to run it. The challenges
here therefore build the ideas by hand. You get a tiny `Pause` object:
`await Pause()` is the smallest possible await point.

1. **`mini-loop`**: write `run_all(coroutines)`, a round-robin loop that drives
   coroutines one step at a time with `coro.send(None)`, collects their return
   values from `StopIteration.value`, and returns them in input order. You will
   see that an event loop is just a list of tasks taking turns.
2. **`limiter`**: write `Limiter(limit)`, an async context manager (`__aenter__`
   and `__aexit__`) that lets at most `limit` tasks inside at once. It is the
   idea behind `asyncio.Semaphore`.

Run them in the browser editor, or locally with `python tests.py <file>`. The
lesson examples above need a real Python with `asyncio`; try them in a terminal.

**Why `__aexit__` matters.** It runs when the block ends normally and when it
ends with an exception, which makes it the right place to give a place back.
Returning a true value from `__aexit__` would hide the exception, so return
`False`.

## L4. Production reality

- **Concurrency is for waiting.** Use it when the time goes on the network,
  disk or a timer, for example many API calls. For heavy number crunching, use
  processes, or vectorised libraries.
- **Never block the loop.** One `time.sleep`, one `requests.get`, one big loop
  in a coroutine stalls every task. Use async libraries, `asyncio.to_thread` for
  unavoidable blocking calls, and keep coroutines short between awaits.
- **Limit concurrency.** Firing thousands of requests at once trips rate limits
  and exhausts sockets. Use a `Semaphore` or a fixed set of worker tasks.
- **Set timeouts.** A network call with no timeout can wait forever. Wrap calls
  in `asyncio.timeout` and decide what a timeout means.
- **Handle errors and cancellation on purpose.** `gather` leaves other tasks
  running when one fails. A `TaskGroup` cancels the rest. If you catch
  `CancelledError`, re-raise it so cancellation can finish.
- **Keep a reference to every task you create.** The event loop holds only a weak
  reference, so a task nobody else refers to can be garbage-collected before it
  finishes. Keep tasks in a list or use a `TaskGroup`.
- **Do not forget `await`.** A missing `await` is silent apart from a warning,
  and the work never happens. Treat the "never awaited" warning as a bug.
- **Mixed worlds.** `asyncio.run` should be the one entry point of a program. It
  cannot be called from inside a running loop. Async frameworks give you an
  already-running loop; just `await`.
- **Failure at 3 a.m.:** latency is the sum of all calls instead of the longest
  (you awaited in a loop instead of gathering), or everything stalls together
  (something blocking sits in a coroutine), or a job "works" but never ran (a
  missing await).
